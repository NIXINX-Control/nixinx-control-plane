# P02-02 — Product catalog reconciliation candidate

This extends the existing superadmin-only product PLAN, not the production catalog API. Provider discovery must succeed first; catalog reads are performed in one read-only Firestore transaction. The pure planner compares the canonical apps and appModules document IDs against the manifest fetched from main at its exact commit. It returns deterministic missing/reuse/verify/blocked steps. Existing names, active/draft/retired state, verification flags and IDs are preserved; case conflicts, orphan modules and inconsistent bindings block. Missing module candidates may only become draft/unverified in a future authorized APPLY. No new collections, status values in Firestore, licenses, customers, secrets, or writes.

Limitations: current app catalog does not attest GitHub/Vercel identity. Existing app name is not proof of ownership. No automatic adoption or overwrite, no activation. Existing app status supports active/archived only; do not introduce a new persisted status or create an active app before approving the registration gate. The 500-record bounded complete scans match the existing precheck strategy but deliberately fail closed above the limit; indexed uniqueness and migration strategy require separate review before scale certification. A repeat plan is deterministic, not proof of transactional idempotent APPLY. Provider identity, release, domain, runtime and data authorization remain unverified live.

Next gate: reconcile existing app bindings and define a durable verified product identity/commit receipt using the current catalog (candidate, not approved schema); design transactional create-if-absent, no overwrite, concurrency and readback after authorized release. Review minimal provider credentials and the Initiatives legacy workflow/public repository gate. No merge, deployment or live APPLY by this change.
